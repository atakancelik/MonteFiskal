## Schema observations

Facts read directly from the schema that a code generator or a validator must respect. IDs are referenced from `business-rules.md`.

| ID | Observation | Where |
|---|---|---|
| S-01 | Every request root carries `Id="Request"` and `Version="1"` as **fixed** values; responses carry `Id="Response"`, `Version="1"`. | root elements |
| S-02 | Request and response roots use `xs:all`: `Header`, the payload element and `ds:Signature` are all mandatory, order free. The signature is a child of the root element (enveloped signature). `InvoiceType` is also `xs:all`, so its child elements may come in any order. | root elements, `InvoiceType` |
| S-03 | Monetary totals (`DecimalSType`, `DecimalNegSType`) must be written with **exactly two** decimals, or as the literal `0`. `12.5`, `12.500` and `-0` are schema-invalid; `-0.00` is schema-valid. | simple types |
| S-04 | Item-level amounts (`Decimal4SType`, `Decimal4NegSType`: `UPB`, `UPA`, `R`, `PB`, `VR`, `VA`, `PA`) and `SameTax/@PriceBefVAT`, `SameTax/@VATAmt` take **two to four** decimals, or the literal `0`. `SameTax/@VATRate` takes exactly two. | `InvoiceItemType`, `SameTaxType` |
| S-05 | Quantity `Q` is an `xs:double` restricted to at most three decimals, sign allowed, no exponent notation. | `DoubleNegForQuantitySType` |
| S-06 | `UPB`, `UPA`, `R`, `VR` cannot be negative; `PB`, `VA`, `PA`, `Q` and the invoice-level totals can. `TotPriceToPay` and `CashDeposit/@CashAmt` cannot be negative. Corrections are therefore expressed through negative quantities and totals, never negative unit prices. | simple types |
| S-07 | Date-times must match `YYYY-MM-DDThh:mm:ss` followed by `Z` or `±hh:mm`. Fractional seconds are schema-invalid; a time-zone designator is mandatory. | `UTCSType` |
| S-08 | `IIC` is 32 hex characters (128 bit); `IICSignature` is exactly 512 hex characters (2048 bit). The schema therefore only admits a signature produced with a 2048-bit RSA key. Both upper and lower case hex digits are schema-valid. | `Hex32SType`, `Hex512SType` |
| S-09 | Registration codes (business unit, TCR, software, maintainer, operator) all share one pattern: two lowercase letters, three digits, two lowercase letters, three digits. | `RegistrationCodeSType` |
| S-10 | `InvNum` = `<BusinUnitCode>/<InvOrdNum>/<4-digit year>/<TCRCode>`; the ordinal has 1 to 15 digits and no leading zero. The schema's own description of `InvNum` ("ordinal number, year … and code of TCR") is older than its pattern and omits the business unit code. | `InvNumSType` |
| S-11 | `Invoice/@TCRCode` is **required** for every invoice, cash or non-cash, and is also a mandatory part of `InvNum`. | `InvoiceType` |
| S-12 | `TINSType` accepts 8 digits (PIB) or 13 digits (JMB). It is used for `IssuerTIN` in TCR and cash-deposit messages. The invoice message has **no** `IssuerTIN` attribute; the seller is identified by `Seller/@IDType` + `Seller/@IDNum` (free string, 1..20). | `TCRType`, `CashDepositType`, `SellerType` |
| S-13 | `PayMethods` holds 1..10 `PayMethod` elements and a uniqueness constraint on `@Type`: one invoice cannot list the same payment method twice. `Fees` has the same constraint on `Fee/@Type`. | `xs:unique` |
| S-14 | Limits: 1..1000 items, 1..20 `SameTax` groups, 1..20 `Approval` rows, 1..20 fees, 1..1000 `IICRef` references, 1..20 vouchers per payment method. | sequences |
| S-15 | `Items` is **optional** (0..1) and `SameTaxes` is optional. Inside a `SameTax`, `VATRate`, `VATAmt` and `ExemptFromVAT` are all optional, so both "rate + amount" and "exemption code" shapes are admitted. `Invoice/@TotVATAmt` is optional too. | `InvoiceType`, `SameTaxType` |
| S-16 | `Buyer` is optional, but when present `IDType`, `IDNum` and `Name` are required. Any rule that makes the buyer mandatory (for example for non-cash invoices) is a business rule, not a schema rule. | `BuyerType` |
| S-17 | The currency enumeration contains `EUR`; `Currency` is optional. `ExRate` is a positive `xs:double` described as the amount of EUR for one unit of foreign currency. | `CurrencyType` |
| S-18 | `TCRType` is a `simpleContent` extension of `xs:string`: the `TCR` element may carry text content next to its attributes. No meaning is documented for that text; an empty element is valid. | `TCRType` |
| S-19 | `RegisterTCRRequest/Header` has no `SubseqDelivType`; only invoice and cash-deposit headers do. | header types |
| S-20 | `xs:documentation` texts for several attributes are visibly copy-pasted or stale (for example `TypeOfInv` is described as an item type, `Approval/@ExemptFromVAT` is typed as a decimal amount although its name matches an enumeration elsewhere). Descriptions are therefore weak evidence. | whole schema |
| S-21 | Three complex types are declared but not referenced by any element: `VouchersSoldType`, `VoucherSoldDataType`, `VouchersSoldNumType`. They are listed under `complexTypes` in the JSON and must not be generated into the public model. Sold-voucher data is carried by the item attributes `VD` and `VSN`. | complex types |
| S-22 | `PaymentMethodTypeSType` contains a value with a hyphen, `OTHER-CASH`; it cannot be mapped to an identifier by name without an explicit mapping. | enumerations |
| S-23 | The schema declares `vc:minVersion="1.1"` and imports `xmldsig-core-schema.xsd` by relative location (served next to it, SHA-256 `3c6f965494dbbb62db13d9261739c36068010fc9be0b019785570d63d9ac42ed`). Two patterns, `InvNumSType` and `TaxPeriodSType`, escape the slash as `\/`. This escape is not part of the XSD regular-expression grammar: libxml2 2.9.14 (`xmllint`, and therefore PHP `DOMDocument::schemaValidate`) refuses to compile the unmodified schema with "Wrong escape sequence". With the two `\/` replaced by `/` the schema compiles and validates under libxml2 (checked on 2026-11-13). Behaviour of the .NET validator on the unmodified file is UNVERIFIED. | schema root, `InvNumSType`, `TaxPeriodSType` |
| S-24 | The WSDL declares a SOAP 1.1 document/literal binding with one `soapAction` per operation. The response of every operation has the same shape: header with `UUID`, `RequestUUID`, `SendDateTime`, one result element (`FIC`, `TCRCode`, `FCDC`) and a signature. | WSDL, response elements |

### Schema drift

The live schema differs from both older public copies. The table lists what changed; the left column is the live schema this catalog describes.

| Live schema (2026-11-13) | Community mirror dated 2022 (see `sources/README.md`, R-04) | Technical specification v02 annex (2020) |
|---|---|---|
| `Invoice/@InvType` required (`INVOICE`, `CORRECTIVE`, `SUMMARY`, `PERIODICAL`, `ADVANCE`, `CREDIT_NOTE`) | absent; `IsSimplifiedInv` present instead | absent |
| `Invoice/@TCRCode` required | optional | optional |
| `InvNum` = BU/ordinal/year/TCR | same | ordinal/year with optional TCR |
| `IsReverseCharge` optional | required | required |
| `Buyer` `IDType`, `IDNum`, `Name` required when buyer present | optional | optional |
| `Items` optional | required | required |
| Seller and buyer `Name` up to 400 characters | 100 | 100 |
| `TotPriceToPay`, `BankAccNum`, `Note`, `PayMethod/@AdvIIC`, `PayMethod/@BankAcc`, `Buyer/@TIC`, `I/@VD`, `I/@VSN`, `Approvals`, `IICRefs` with `Amount` | absent (`SumInvIICRefs` instead of `IICRefs`; voucher data as child elements of the item) | absent |
| Payment methods: `BANKNOTE`, `CARD`, `BUSINESSCARD`, `SVOUCHER`, `COMPANY`, `ORDER`, `ADVANCE`, `ACCOUNT`, `FACTORING`, `OTHER`, `OTHER-CASH` | `BUSINESS-CARD` spelling | older list including `CHECK`, `COMPENSATION`, `TRANSFER`, `WAIVER`, `KIND` |
| Corrective types `CORRECTIVE`, `ERROR_CORRECTIVE` | `CORRECTIVE`, `DEBIT`, `CREDIT` | as mirror |
| Fee types `PACK`, `COMMISSION`, `OTHER` | also `BOTTLE` | as mirror |
| Exemption codes include `VAT_CL3`, `VAT_CL4`, `VAT_CL14`, `VAT_CL15`, `VAT_CL44` | absent | absent |
| `SameTax/@PriceBefVAT`, `@VATAmt` two to four decimals | exactly two | exactly two |

Compared with the technical specification **v5** (D-07, 2021), which was read after this table was built, the live schema is still slightly newer: v5's text lists the late-delivery value as `BUSINESSNEED` (live: `BUSINESSNEEDS`), the fee type as `COMMISION` (live: `COMMISSION`), self-issue kinds without `SELF`, exemption codes without `VAT_CL3`, `VAT_CL4`, `VAT_CL14`, `VAT_CL15`, names of 100 characters and `Items` as part of every invoice. v5's own version table records the earlier steps: v3 added `ADVANCE`; v4 changed patterns and added `BUSINESSNEED`; v4.1 added `TaxPeriod`, the `mapr` verification host, mandatory TCR code and the new invoice number; v5 added `InvType`, `TotPriceToPay`, `BankAccNum`, `Note`, `IICRefs`, `AdvIIC`, `BankAcc`, `TIC`, `VD`, `VSN`, `Approvals` and removed `BOTTLE`, with the old forms accepted until 1.10.2021. Element meanings are in `business-rules.md` section 8.

The request `Version` attribute stayed fixed at `1` and the endpoint stayed `fs-v1` through all of these changes. A client cannot detect the schema revision from the version number; see `architecture.md` §5.
