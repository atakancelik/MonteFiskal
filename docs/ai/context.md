## 1. What MonteFiskal is

MonteFiskal is an open-source client for Montenegro's EFI fiscalization service (Poreska uprava, the Tax Administration):
a .NET 10 library, a PHP 8.5 core with the same API, and a WooCommerce plugin built on the PHP core.
It builds the request, computes the IKOF, signs the XML, sends it, retries it and keeps every request and response.

It is not a hosted service, not accounting advice and not a certificate provider. The taxpayer brings its own qualified
certificate and its own codes from the SEP portal. Montenegro's rules differ from Croatia's, Serbia's and Albania's:
use the rules quoted here, never general knowledge about other countries.

Before writing code, ask the developer the intake questions in `docs/ai/questions.md`.

## 2. The three operations

| Operation | When | Rule |
|---|---|---|
| Register TCR | Once per cash register or web shop; the code is permanent | BR-R5 |
| Register cash deposit | The day's `INITIAL` deposit before the first cash invoice of that day (0.00 is allowed); `WITHDRAW` when cash is taken out | BR-D1, BR-D5 |
| Register invoice | Every invoice, cash or non-cash | BR-S1 |

> **BR-D5**: A TCR in a business unit registered **only for non-cash invoices** has no duty to send the initial deposit. A TCR in a business unit registered for cash invoices must send it before the first invoice of the day. The official FAQ gives the reason: such a unit "has no cash (`BANKNOTE`) as a payment method". The software **must have a built-in control that refuses to fiscalize a cash invoice before the day's `INITIAL` deposit is registered** for that TCR; the service answers code 58 otherwise. Consequence for a web shop: consumer card payments are `CASH` invoices (BR-K1, BR-K3), so its TCR sits in a cash business unit and needs an `INITIAL` of `0.00` every day on which it issues a cash invoice. The plugin must send it automatically.

## 3. The life of an invoice

1. Draft: lines, payments, buyer when the buyer is a company with a tax number.
2. Issue (local, no network): validation, calculation, the next ordinal of the sequence, the invoice number, the IKOF and
   the verification URL. From now on the number and the IKOF are final.
3. Send: signed request; the answer is the JIKR (FIC).
4. Print or e-mail: invoice number, IKOF, JIKR, QR code (at least 21 mm), operator and software code.
5. When sending fails: hand the invoice over anyway (IKOF without JIKR) and resend within 48 hours. Never renumber.

> **BR-J2**: An invoice that could not be registered is still issued with the IKOF only (no JIKR) and must be registered later with the same IKOF.

> **BR-O7**: A resent invoice has identical content and identical IKOF. Only the header changes: new `UUID`, new `SendDateTime`, and `SubseqDelivType` set. `IssueDateTime` stays the original time. The request signature is recomputed.

> **BR-C1**: A registered invoice cannot be deleted or changed. It is corrected by a corrective invoice that references the original IKOF.

## 4. Payment method decides the invoice type

> **BR-K3**: Payment method and allowed `TypeOfInv`: `BANKNOTE` (notes and coins) → `CASH`; `CARD` (bank credit or debit card **issued to a natural person**) → `CASH`; `OTHER-CASH` → `CASH`; `BUSINESSCARD` (bank card issued to a taxpayer) → `NONCASH`; `SVOUCHER` → `NONCASH`; `COMPANY` → `NONCASH`; `ADVANCE` → `NONCASH`; `ACCOUNT` (bank transfer) → `NONCASH`; `FACTORING` → `NONCASH`; `OTHER` → `NONCASH`; `ORDER` (not yet paid, will be paid by summary invoice) → `CASH` and `NONCASH`. The schema does not express this; enforce it locally. Open detail: a payment gateway usually cannot tell a consumer card from a company card (Q-29).

A consumer paying by card online produces a **cash** invoice, so the TCR needs the day's `INITIAL` deposit (BR-D5)
and the buyer needs a paper invoice (BR-P4).

## 5. Corrections

An invoice is never edited or deleted. A refund is a corrective invoice that references the original IKOF; a full refund
negates every quantity, a partial refund carries only the refunded lines. The corrective invoice is sent only after the
original has its JIKR.

> **BR-C3**: The original must be registered before the corrective invoice is sent.

> **BR-C5**: Partial correction: only the affected item is sent, with negative quantity and amounts; the examples annex shows this on a non-cash invoice. A corrective invoice references exactly one original IKOF. A reduction that spans several invoices is made with a credit note (BR-K18) or, in the annex's example, a summary invoice followed by its corrective. A cash refund is accompanied by a `WITHDRAW` message (official FAQ; consistent with BR-D3).

## 6. Minimal correct code

Both samples run in CI against the in-process fake service (`MonteFiskal.Testing`, `MonteFiskal\Testing`). The values

### .NET

<!-- sample: tools/ai-kit/samples/dotnet/FirstInvoice.cs -->
```csharp
// Minimal correct path in .NET: configure, issue, send, handle the result, resend pending.
// Runs against the in-process fake service; for efitest replace the transport and the certificate provider.
using MonteFiskal;
using MonteFiskal.Model;
using MonteFiskal.Outbox;
using MonteFiskal.Security;
using MonteFiskal.Testing;

var profile = new FiscalProfile
{
    Environment = FiscalEnvironment.Test,
    IssuerTin = "12345678",              // <your TIN>; this value belongs to the fake service only
    IssuerName = "MonteFiskal Test Only DOO",
    IssuerInVat = true,
    BusinessUnit = "bb123bb123",         // <your business unit code>
    Tcr = "cc123cc123",                  // <your TCR code>
    Software = "ss123ss123",             // <your software code>
    Operator = "oo123oo123",             // <your operator code>
};
// Production: Pkcs12CertificateProvider.FromEnvironment("<path outside the repository>.p12", "MONTEFISKAL_CERT_PASSWORD")
var certificates = new StaticCertificateProvider(TestCertificateFactory.Create(profile.IssuerTin));
var store = new InMemoryOutboxStore();   // production: MonteFiskal.Storage.EntityFrameworkCore
var client = new FiscalClient(profile, certificates, new FakeEfiEndpoint(), store);

var issued = await client.IssueInvoiceAsync(new InvoiceDraft
{
    Lines = [new InvoiceLine { Name = "Item", Unit = "kom", Quantity = 2, UnitPrice = 12.10m, VatRate = 21, PriceIncludesVat = true }],
    Payments = [new Payment { Method = PaymentMethod.Card }],   // consumer card: a CASH invoice (BR-K3)
});
// The invoice exists now: number and IKOF are final, even if sending fails (BR-J2).
var sent = await client.SendAsync(issued.Id);
if (sent.State != InvoiceState.Fiscalized)
{
    // Never renumber; the resend keeps body and IKOF (BR-O7). Run this periodically.
    await client.ResendPendingAsync(new ResendOptions());
}
Console.WriteLine($"{issued.Number} IKOF {issued.Iic} JIKR {sent.Fic} {issued.VerificationUrl}");
return sent.State == InvoiceState.Fiscalized ? 0 : 1;
```

```php
<?php

// Minimal correct path in PHP 8.5: configure, issue, send, handle the result, resend pending.
// Runs against the in-process fake service; for efitest use CurlTransport and Pkcs12CertificateProvider.

declare(strict_types=1);

use MonteFiskal\Model\InvoiceState;
use MonteFiskal\Model\Payment;
use MonteFiskal\Model\PaymentMethod;
use MonteFiskal\Outbox\InMemoryOutboxStore;
use MonteFiskal\Security\StaticCertificateProvider;
use MonteFiskal\Testing\FakeEfiEndpoint;
use MonteFiskal\Testing\TestCertificateFactory;

$profile = new FiscalProfile(
    issuerTin: '12345678',          // <your TIN>; this value belongs to the fake service only
    issuerName: 'MonteFiskal Test Only DOO',
    businessUnit: 'bb123bb123',     // <your business unit code>
    software: 'ss123ss123',         // <your software code>
    operator: 'oo123oo123',         // <your operator code>
    tcr: 'cc123cc123',              // <your TCR code>
    issuerInVat: true,
);
// Production: Pkcs12CertificateProvider::fromEnvironment() reads MONTEFISKAL_CERT_PATH and MONTEFISKAL_CERT_PASSWORD.
$certificates = new StaticCertificateProvider(TestCertificateFactory::create($profile->issuerTin));
$client = new FiscalClient($profile, $certificates, new FakeEfiEndpoint(), new InMemoryOutboxStore());

$issued = $client->issueInvoice(new InvoiceDraft(
    lines: [new InvoiceLine('Item', 'kom', '2', '12.10', priceIncludesVat: true, vatRate: '21')],
    payments: [new Payment(PaymentMethod::Card)],   // consumer card: a CASH invoice (BR-K3)
));
// Amounts are decimal strings, never floats. Number and IKOF are final now (BR-J2).
$sent = $client->send($issued->id);
if ($sent->state !== InvoiceState::Fiscalized) {
    $client->resendPending();   // never renumber; body and IKOF stay (BR-O7)
}
echo "{$issued->number} IKOF {$issued->iic} JIKR {$sent->fic} {$issued->verificationUrl}\n";
exit($sent->state === InvoiceState::Fiscalized ? 0 : 1);
```

### WooCommerce

Install the release zip, define `MONTEFISKAL_CERT_PATH` and `MONTEFISKAL_CERT_PASSWORD` in `wp-config.php` (certificate
outside the web root), run WooCommerce > MonteFiskal > setup wizard, map every payment gateway and zero-rate tax class.
The plugin issues at payment, sends through Action Scheduler and registers the daily deposit itself. Check with
`wp montefiskal status`.

## 8. Mistakes to avoid

| Mistake | Rule |
|---|---|
| Computing the IKOF yourself instead of calling the library | BR-I1 |
| Floating-point money (`double`, `float`) | BR-A5 |
| Treating a consumer card payment as non-cash | BR-K3 |
| Generating a new invoice number on retry | BR-O7 |
| Sending to production from a test | BR-T1 |
| Inventing `SoftCode` or `MaintainerCode` | BR-R7 |
| Storing the certificate in the repository or the web root | BR-S1 |
| Deleting or updating a fiscalized invoice instead of issuing a corrective | BR-C1 |
| Applying Croatian, Serbian or Albanian rules | the rule book only |
| Skipping the initial cash deposit on a day with cash invoices | BR-D5 |
