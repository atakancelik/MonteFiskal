## 1. What MonteFiskal is

MonteFiskal is an open-source client for Montenegro's EFI fiscalization service (Poreska uprava, the Tax Administration):
a .NET 10 library, a PHP 8.5 core with the same API, and a WooCommerce plugin built on the PHP core.
It builds the request, computes the IKOF, signs the XML, sends it, retries it and keeps every request and response.

It is not a hosted service, not accounting advice and not a certificate provider. The taxpayer brings its own qualified
certificate and its own codes from the SEP portal. Montenegro's rules differ from Croatia's, Serbia's and Albania's:
use the rules quoted here, never general knowledge about other countries.

Before writing code, ask the developer the intake questions in `docs/ai/questions.md`.

## 2. The three operations

| Operation | When | Rule |
|---|---|---|
| Register TCR | Once per cash register or web shop; the code is permanent | {{ruleid:BR-R5}} |
| Register cash deposit | The day's `INITIAL` deposit before the first cash invoice of that day (0.00 is allowed); `WITHDRAW` when cash is taken out | {{ruleid:BR-D1}}, {{ruleid:BR-D5}} |
| Register invoice | Every invoice, cash or non-cash | {{ruleid:BR-S1}} |

## 3. The life of an invoice

1. Draft: lines, payments, buyer when the buyer is a company with a tax number.
2. Issue (local, no network): validation, calculation, the next ordinal of the sequence, the invoice number, the IKOF and
   the verification URL. From now on the number and the IKOF are final.
3. Send: signed request; the answer is the JIKR (FIC).
4. Print or e-mail: invoice number, IKOF, JIKR, QR code (at least 21 mm), operator and software code.
5. When sending fails: hand the invoice over anyway (IKOF without JIKR) and resend within 48 hours. Never renumber.

## 4. Payment method decides the invoice type

{{rule:BR-K3}}

A consumer paying by card online produces a **cash** invoice, so the TCR needs the day's `INITIAL` deposit ({{ruleid:BR-D5}})
and the buyer needs a paper invoice ({{ruleid:BR-P4}}).

## 5. Corrections

An invoice is never edited or deleted. A refund is a corrective invoice that references the original IKOF; a full refund
negates every quantity, a partial refund carries only the refunded lines. The corrective invoice is sent only after the
original has its JIKR.

### WooCommerce

Install the release zip, define `MONTEFISKAL_CERT_PATH` and `MONTEFISKAL_CERT_PASSWORD` in `wp-config.php` (certificate
outside the web root), run WooCommerce > MonteFiskal > setup wizard, map every payment gateway and zero-rate tax class.

`wp montefiskal status`.

## 8. Mistakes to avoid

| Mistake | Rule |
|---|---|
| Computing the IKOF yourself instead of calling the library | {{ruleid:BR-I1}} |
| Floating-point money (`double`, `float`) | {{ruleid:BR-A5}} |
| Treating a consumer card payment as non-cash | {{ruleid:BR-K3}} |
| Generating a new invoice number on retry | {{ruleid:BR-O7}} |
| Sending to production from a test | {{ruleid:BR-T1}} |
| Inventing `SoftCode` or `MaintainerCode` | {{ruleid:BR-R7}} |
| Storing the certificate in the repository or the web root | {{ruleid:BR-S1}} |
| Deleting or updating a fiscalized invoice instead of issuing a corrective | {{ruleid:BR-C1}} |
| Applying Croatian, Serbian or Albanian rules | the rule book only |
| Skipping the initial cash deposit on a day with cash invoices | {{ruleid:BR-D5}} |
